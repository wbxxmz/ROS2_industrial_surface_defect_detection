# 工业产品表面缺陷检测平台 · 实现文档

> 版本：V1.0（粗略指导版）
> 适用对象：项目负责人 / 开发人员 / 质检业务人员
> 定位：通用质检工具 —— 可替换检测算法、可导入自有数据集、可输出质量报告

---

## 一、产品需求深度分析

### 1.1 产品定位

本产品不是"某个产品的定制检测程序"，而是一个**通用表面缺陷质检平台**。它的核心价值在于三点：

1. **算法可替换**：传统 OpenCV 算法与 YOLO 系列深度学习模型可以像插件一样插拔，同一套界面与流程适配不同算法。
2. **数据集可导入**：用户能带入自己的产品照片/视频训练或调参，平台不绑定单一行业或单一缺陷。
3. **报告可输出**：检测结果沉淀为结构化质检报告，而非一次性弹出窗口。

产品从"检测工具"升级为"质检基础设施"，本质是对"缺陷 → 决策 → 记录"完整闭环的抽象。

### 1.2 目标用户与使用场景

| 角色 | 核心诉求 | 高频操作 |
| --- | --- | --- |
| 质检工程师 | 快速看缺陷在哪、有多大、严重吗 | 上传图片/对接摄像头、看懂结果标注 |
| 算法工程师 | 更换/对比算法、调参、导入数据集重训练 | 切换模型、看精度/速度/内存对比 |
| 产线管理者 | 统计良率、追溯质量、导出报告 | 批量检测、生成并下载质检报告 |

典型场景：
- **离线抽检**：单张/多张图片批量检测。
- **产线实时**：摄像头/工业相机流式检测，实时框出缺陷。
- **算法选型**：同一批缺陷样本，对比不同算法的检测效果与资源消耗，辅助决策。

### 1.3 核心需求拆解

#### 基础版本需求（MVP）

1. **多输入源支持**
   - 图片：单张上传、批量目录导入。
   - 视频：本地视频文件逐帧检测。
   - 摄像头：RTSP/USB 摄像头实时流。
   - 三者应共用同一套"帧 → 检测 → 结果"的处理管线。

2. **缺陷类型覆盖**
   - 划痕（scratch）：细长线状缺陷。
   - 凹坑（dent/pit）：点状或局部凹陷。
   - 污渍（stain）：颜色/纹理异常区域。
   - 缺口（notch/chip）：边缘破损。
   - 需求要求"检测"，即至少完成**目标检测 + 分类**，并预留缺陷类型可扩展。

3. **双算法路线**
   - 传统 OpenCV：基于图像处理（滤波、阈值、形态学、边缘检测、轮廓分析等）实现，无需标注、无需训练、可解释性强。
   - YOLO 系列：YOLOv5/v8/v11 等，需标注数据训练，泛化能力强、针对复杂缺陷。
   - 关键难点：**两套算法的输入/输出必须统一抽象**，否则"可替换"就是空谈。

4. **结果展示**
   - 缺陷位置：边界框（bounding box）+ 分割掩码（可选）。
   - 缺陷面积：像素面积与相对占比。
   - 置信度：0–100% 概率输出。
   - 检测结果：缺陷类别、数量汇总、单件产品合格/不合格判定。

#### 创新空间需求（进阶）

1. **小样本缺陷检测**：真实产线中缺陷样本稀缺（可能只有几十张），需研究少样本学习、数据增强、迁移学习、合成缺陷等手段。
2. **无监督异常检测**：只用正常样本训练（如 PatchCore、PaDiM、自编码器重构），适合"不知道会出现什么新缺陷"的场景。
3. **缺陷严重程度分级**：由"有没有缺陷"升级为"缺陷有多严重"，为分级放行/报废决策提供依据。
4. **误报分析**：统计误报率、误报类型、误报原因，帮助用户理解算法边界，避免产线因误报瘫痪。
5. **算法多维对比**：精度（mAP/召回/精确率）、速度（FPS/单帧耗时）、内存/显存占用（MB）统一评测，输出对比表。
6. **质检报告生成**：包含检测概览、缺陷明细、良率统计、缺陷分布图，可导出 PDF/Word/Excel。

### 1.4 需求优先级（MoSCoW）

| 优先级 | 需求项 |
| --- | --- |
| Must（必须有） | 图片/视频/摄像头输入；划痕/凹坑/污渍/缺口检测；位置/面积/置信度展示 |
| Should（应该有） | 传统 OpenCV + YOLO 双算法；统一算法接口；基础结果可视化 |
| Could（可以有） | 小样本检测、无监督异常检测、严重度分级、误报分析、算法对比、报告生成 |
| Won't（暂不做） | 三维表面缺陷、多光谱/红外检测、云端分布式训练、移动端 App |

> 说明：MVP 先做 Must + Should；创新空间（Could）作为可迭代的增量能力，按投入产出比逐个落地。

### 1.5 关键痛点与风险

1. **数据不平衡**：正常品远多于缺陷品 → 训练与评测都要处理类别不平衡，避免"全判正常也能拿高分"的假象。
2. **缺陷形态多样**：同一种"划痕"可能深浅、粗细、方向各异 → 不能只靠单一特征，需要组合方法与数据增强。
3. **光照/背景干扰**：反光、油污、纹理背景会造成误报 → 需要预处理与硬件打光配合。
4. **实时性 vs 精度**：摄像头场景对 FPS 有要求，深度学习模型需在算力与精度间权衡。
5. **算法可替换性**：若接口设计不统一，后续换算法/加算法会反复返工 → 架构上必须优先抽象。

### 1.6 验收方向（怎么算"做好"）

- 单类缺陷检测（某一种算法）达到可用召回率，误报率可接受。
- 用户无需改代码即可在界面切换 2 种以上算法。
- 导入自己的图片/视频能跑通完整检测并出报告。
- 报告能真实反映缺陷位置、面积、置信度与总体良率。

## 二、总体架构设计

### 2.1 分层架构

```
┌─────────────────────────────────────────────┐
│  展示层   UI / 结果可视化 / 报告预览          │
├─────────────────────────────────────────────┤
│  应用层   检测任务编排 / 批量处理 / 对比评测    │
├─────────────────────────────────────────────┤
│  算法层   统一检测接口                        │
│      ├─ OpenCV 传统算法 (可插拔)             │
│      └─ YOLO 系列模型 (可插拔)               │
├─────────────────────────────────────────────┤
│  数据层   输入采集(图片/视频/摄像头)          │
│          数据集管理 / 结果存储 / 报告存储      │
└─────────────────────────────────────────────┘
```

### 2.2 关键设计原则

1. **统一检测接口（核心）**：所有算法实现同一个抽象接口，例如 `detect(frame) -> List[Detection]`，其中 `Detection` 统一包含类别、边界框、掩码、面积、置信度。这是"可替换算法"的技术根基。
2. **统一结果数据结构**：面积、位置、置信度的计算口径在接口层统一，避免不同算法各自为政。
3. **流水线化处理**：`采集 → 预处理 → 检测 → 后处理 → 标注/判定 → 存储/出报告` 拆成可独立替换的环节。
4. **算法即插件**：通过配置或工厂模式注册算法，新增算法不改主流程。

### 2.3 技术选型建议

| 层 | 建议 | 理由 |
| --- | --- | --- |
| UI / 可视化 | Python + Qt(PySide6) 或 Web(Flask/FastAPI + 前端) | 图像预览、框标注、报告展示友好 |
| 图像处理 | OpenCV、NumPy | 行业标准，覆盖传统算法与预处理 |
| 深度学习 | PyTorch + ultralytics(YOLO) | YOLO 系列训练/推理成熟 |
| 摄像头接入 | OpenCV VideoCapture / RTSP | 统一视频流读取 |
| 报告生成 | matplotlib + reportlab / openpyxl | 图表 + PDF/Excel 导出 |
| 数据管理 | 本地文件目录 + JSON/CSV 标注清单 | 轻量、可审计、易迁移 |

## 三、实现阶段划分与阶段要求

> 每个阶段列出目标、主要工作、交付物与验收要求。整体遵循"先跑通闭环，再逐项增强"。

### 阶段 0：需求与总体设计

- **目标**：冻结需求范围与技术方案，定好接口契约。
- **工作**：需求评审、架构定稿、确定统一检测接口与结果数据结构、制定里程碑。
- **交付物**：需求清单（MoSCoW）、架构图、接口定义文档。
- **阶段要求**：明确 MVP 边界与验收标准；`Detection` 数据结构、`detect()` 接口签名全组对齐。

### 阶段 1：基础框架搭建

- **目标**：搭起可运行的工程骨架。
- **工作**：工程目录、依赖管理、日志与配置、异常处理、单元测试骨架、算法接口的抽象父类。
- **交付物**：可启动的工程 + 空实现的检测流水线。
- **阶段要求**：能用一张占位图跑通"加载 → 检测(空实现) → 输出空结果"的端到端流程。

### 阶段 2：输入源实现

- **目标**：三种输入源统一接入。
- **工作**：
  - 图片：单张 + 批量目录。
  - 视频：逐帧读取、跳帧/抽帧控制。
  - 摄像头：本地 USB + RTSP 流、实时帧队列。
- **交付物**：输入抽象层，返回统一格式的帧。
- **阶段要求**：三种来源都能稳定产出帧供后续处理；视频/摄像头支持暂停、逐帧、播放控制。

### 阶段 3：传统 OpenCV 算法实现

- **目标**：不依赖训练数据，先做出可用的缺陷检测。
- **工作**：预处理（去噪、光照校正）→ 特征提取（滤波、阈值、边缘、形态学、轮廓）→ 后处理（连通域、过滤、面积/几何约束）→ 缺陷分类与定位。
- **交付物**：OpenCV 检测器（实现统一接口），覆盖划痕/凹坑/污渍/缺口四类。
- **阶段要求**：在给定样本上四类缺陷均有可接受的检出，输出位置、面积、置信度（可用规则分数近似）。

### 阶段 4：YOLO 模型集成

- **目标**：接入深度学习路线，实现真正的"双算法"。
- **工作**：数据标注准备（或工具集成）→ 模型训练 → 推理封装为统一接口 → 与 OpenCV 结果对照。
- **交付物**：YOLO 检测器（可插拔）+ 训练/推理脚本。
- **阶段要求**：同一批样本上 YOLO 与 OpenCV 输出同构结果，可在界面切换；YOLO 对复杂缺陷的泛化优于纯传统方法。

### 阶段 5：结果可视化与判定

- **目标**：把结果清楚地"画出来、判出来"。
- **工作**：边界框/掩码叠加绘制、面积与置信度标注、类别颜色区分、单件合格/不合格判定规则、缺陷统计面板。
- **交付物**：可视化模块 + 判定模块。
- **阶段要求**：位置直观、面积/置信度清晰可读、汇总统计准确。

### 阶段 6：创新功能扩展（按优先级迭代）

- **目标**：把产品从"能检测"推向"更聪明、更可信"。
- **工作（按顺序逐步交付，每项独立可验收）**：
  1. 缺陷严重程度分级（规则 + 面积/深度/位置权重）。
  2. 误报分析（误报率统计、误报样本回溯、原因归类）。
  3. 算法综合对比（精度/速度/内存统一评测表）。
  4. 小样本检测（数据增强、迁移学习、少样本方案）。
  5. 无监督异常检测（正常样本模型，如 PatchCore/PaDiM/重构）。
- **交付物**：上述各子能力的独立模块。
- **阶段要求**：每项能力都有可量化的评测指标，落地前先验证其对真实业务的增益。

### 阶段 7：质检报告生成

- **目标**：输出可交付、可归档的质检报告。
- **工作**：报告模板（检测概览、缺陷明细表、良率、缺陷分布图）→ 一键导出 PDF/Word/Excel → 批量检测自动汇总。
- **交付物**：报告生成模块 + 模板。
- **阶段要求**：报告信息真实、可追溯（含样本标识、算法版本、参数），格式规范。

### 阶段 8：集成测试与优化

- **目标**：保证端到端稳定、可用、可交付。
- **工作**：集成测试、性能优化（FPS、内存）、异常输入处理、边界场景（无缺陷样本、空输入、大图/高分辨率）。
- **交付物**：测试报告 + 性能基线。
- **阶段要求**：关键路径无崩溃；性能指标达到既定阈值；文档齐全。

### 阶段 9：部署与交付

- **目标**：交付一个"别人能上手用"的通用质检工具。
- **工作**：打包/部署方案、用户操作说明、数据集导入说明、算法接入说明。
- **交付物**：可运行版本 + 使用/接入文档。
- **阶段要求**：新用户能独立完成"导入数据 → 选算法 → 出报告"全流程。

## 五、风险与应对（摘要）

| 风险 | 应对 |
| --- | --- |
| 缺陷样本不足 | 数据增强 + 迁移学习 + 合成缺陷；优先无监督/小样本路线 |
| 误报过高 | 预处理 + 打光 + 误报分析 + 置信度阈值调节 |
| 算法接口反复返工 | 阶段 1 先冻结接口契约，后续只增不破坏 |
| 实时性不足 | 抽帧/跳帧、模型量化、分辨率缩放、硬件选型 |
| 需求蔓延 | 严格按 MoSCoW 控制，创新项单独立项 |

## 六、写在最后

本项目成功的关键不在于"多做了哪些算法"，而在于**先做对一件事——把算法真正做成可替换的插件**。只要统一接口与统一结果数据结构立住了，后续无论是换算法、加创新功能、导入新数据集，都是在稳定的骨架上做增量，而不是推倒重来。

建议路线：先以传统 OpenCV 快速打通端到端闭环（投入小、见效快），再引入 YOLO 提升泛化，最后按业务真实需求逐个落地创新项，每一步都要有可量化的评测来证明价值。
