# 阶段 8：集成测试与优化 · 实现技术文档

## 1. 阶段目标

保证系统端到端稳定、可用、可交付，落地性能基线，补齐异常与边界场景处理。本阶段所有验证均为**无头执行**：直接跑脚本/命令、落盘报告，不启动 GUI、不弹窗（延续阶段 5/7 无头架构）。

## 2. 前置条件与依赖

- 依赖阶段 2–7 各模块已实现（输入源、OpenCV/YOLO 检测器、判定、可视化、报告）。
- 依赖阶段 1 的测试骨架与配置体系。
- 运行时依赖：`psutil`（性能监控脚本测峰值内存，必装）；`pytest`（集成/回归用例）。
- 硬件环境：性能基线须标注运行环境（CPU-only 或 GPU/CUDA），两种环境指标不可混比（见 §4.2 / §8）。

## 3. 工作分解（WBS）

1. 集成测试：覆盖"输入 → 检测 → 判定 → 展示 → 报告"完整链路，含端到端场景清单（§4.1）。
2. 性能测试与优化：FPS、单帧耗时、内存/显存占用，交付独立压测脚本（§4.2）。
3. 异常处理：空输入、大图/高分辨率、损坏文件、断流、无缺陷样本，异常隔离（§4.4）。
4. 边界场景：极小缺陷、多缺陷重叠、光照极端样本。
5. 报告聚合校验：报告统计与终端日志逐字段对齐（§4.5）。
6. 文档补齐：运行/接入说明随代码同步更新。

## 4. 关键技术方案

### 4.1 测试分层与端到端场景覆盖

- 单元测试：各算法/模块内部逻辑（阶段 3–7 已各有 `tests/` 用例）。
- 集成测试：固定一批标准样本跑全链路，比对输出与人工标注/金标准。
- 回归测试：算法或接口变更后自动跑标准集，防止退化。

**端到端场景清单（走完整链路 `采集 → 检测 → 判定 → 可视化 → 报告`，四类输入源均不得崩溃）**

| 场景 | 输入源 | 预期（可判定，不含"酌情"） |
| --- | --- | --- |
| 完整批次图片目录 | `image` + `dir`（如 30 张 NEU-DET 验证集） | 逐张处理到底，报告样本数 = 成功处理张数，退出码 0 |
| 单张图片 | `image` + `path` | 正常产出 1 条样本记录与报告 |
| 视频文件 | `video` + `path`（单帧视频也须可读） | 逐帧/抽帧处理到底，读到 `None` 结束，无崩溃 |
| 空目录 | `image` + `dir`（目录存在但无匹配扩展名图片） | **抛 `SourceOpenError`**（§4.4 写死），不生成报告 |
| 损坏图片文件 | `image` + `dir` 中含无法解码的文件 | 主链路 `read()` 抛 `InputSourceError`（fail-fast，阶段 2 契约）；压测脚本逐图隔离不中断（§4.4） |

> 空目录 / 损坏图片分属两条不同路径：前者在 `open()` 阶段即失败（目录为空 → `SourceOpenError`），后者在 `read()` 阶段失败（解码失败 → `InputSourceError`）。两者语义与阶段 2 §5 一致，此处仅做端到端验证，不修改既有契约。

### 4.2 性能基线

统一测量指标（由独立压测脚本采集，不手填）：

| 指标 | 定义 | 单位 | 采集方式 |
| --- | --- | --- | --- |
| 检测 FPS | 检测阶段吞吐 = 1 / 平均单帧 `detect()` 耗时 | 帧/秒 | 逐帧计时（排除模型加载与首次预热） |
| 单帧端到端耗时 | 从 `capture()` 到报告写入完成（含判定/可视化） | ms | 逐图计时 |
| 总耗时（批量 30 张） | 30 张完整处理墙钟时间 | s | 起止 `perf_counter` |
| 峰值内存 | 进程 RSS 峰值 | MB | `psutil.Process().memory_info().rss` |
| 峰值显存 | `torch.cuda.max_memory_allocated()`（仅 GPU） | MB | 推理后重置前读取 |

**性能监控脚本（独立脚本 `scripts/benchmark.py`，交付物之一）**

- 输入：`--config`（检测器/判定/报告配置）、`--limit`（批量张数，默认 30）、`--output`（指标报告路径）。
- 输出：Markdown/JSON 指标报告，含上表 5 项指标 + 错误样本清单与计数。
- **异常隔离（硬性要求）**：逐图 `try/except`；单张损坏图片 → 捕获异常、记 `error` 日志、错误计数 +1、**继续处理**后续图片，不中断整个批次；批次结束把错误样本列入报告。
- 预热语义：首次推理不计入计时（与 `compare_algorithms.py` 口径一致），排除模型加载抖动。

**性能验收阈值（硬性门槛，可配置覆盖）**

- 检测 FPS ≥ **20**（即单帧 `detect()` 平均 ≤ 50 ms）。参考实测：OpenCV ~270 FPS（CPU）、YOLOv8m ~67 FPS（GPU）均远高于门槛。
- 峰值内存：连续对 ≥N 张同分辨率图片处理，批次结束 RSS 较批次前增长有界（不随张数线性/单调累积，判定"无泄漏"）；阈值写入基线表。
- 上述阈值为初始验收值，随阶段 6 算法对比反复测量固化为基线表，不写死在实现代码中（配置化）。

### 4.3 常见优化手段

- 摄像头/视频场景：抽帧/跳帧、分辨率缩放。
- 模型：量化、小模型替换、批处理。
- 传统算法：算子简化、感兴趣区域（ROI）锁定。

> 优化手段仅作为可选方向记录；是否落地由性能基线结果决定，本阶段不预设改动。

### 4.4 异常与边界（异常隔离）

| 情形 | 预期行为（可判定，不含"酌情"） | 异常类型 |
| --- | --- | --- |
| 空输入目录（存在但无匹配图片） | **抛 `SourceOpenError`，不生成空报告**（写死，见下方说明） | `SourceOpenError`（`open` 阶段） |
| 损坏图片（无法解码/为空/尺寸 0） | 主链路 `read()` 抛异常中止该次运行；压测脚本捕获后记错误、跳过、继续 | `InputSourceError`（`read` 阶段） |
| 大图/高分辨率 | 预缩放或分块处理，控制内存峰值；不因单帧过大致 OOM | 按检测器契约 |
| 无缺陷样本 | 正常输出"合格"（`is_pass=True`），不报错不误报 | 无 |
| 断流（视频读尽头/中途 EOF） | `read()` 返回 `None` 正常结束，不视为错误 | 无 |

**空目录语义（写死）**：输入目录为空 → 抛出 `SourceOpenError`，**不生成空报告**。理由：空目录是配置/采集错误，须显式暴露；空批次的 `ValueError` 语义只保留给报告模块自身（`ReportBuilder.build(空 batch)` → `ValueError`），二者不混用。此决策与阶段 2 `ImageSource._collect_dir` 现有行为一致。

### 4.5 报告聚合校验

批量跑完后，落盘的 PDF/Excel 报告统计数字必须与终端日志逐字段一致，作为可自动化的验收环节：

| 报告字段 | 应与日志中哪一项一致 |
| --- | --- |
| 样本数 | 成功处理的样本数（总张数 − 损坏/跳过数） |
| 合格数 / 不合格数 | `summarize()` 的 `pass_count` / `fail_count`，与日志每帧 `is_pass` 汇总一致 |
| 缺陷明细总数（明细表行数） | 日志 `流水线完成：累计 N 条检测结果` 的 N（**原始检出总数**） |
| 概览"缺陷总数"（有效缺陷） | 各帧 `verdict.total_count` 之和（**有效缺陷**，已过置信度/面积阈值） |

> 关键口径：明细表行数 = **原始检出总数**，概览"缺陷总数" = **有效缺陷数**，二者可不等（原始检出中低于阈值的框不计入判定，见阶段 7 §4.4）。校验时必须分别比对，不得混用。

### 4.6 并发与资源生命周期（标注「不适用」）

- 本阶段集成/压测均为**单进程顺序执行**，不引入多线程/并发；不新增对外文件/视频/显存资源的持有逻辑，仅**复用**阶段 2–7 已落地的生命周期（输入源 `open/read/close`、检测器 `load/release`、报告文件句柄释放）。
- 压测脚本中 `psutil` 仅**读取**进程 RSS，不创建/管理外部资源。
- 故本检查项标注「不适用」：本阶段无新增资源所有权或并发模型需声明。

## 5. 关键接口落位

本阶段唯一新增对外入口为性能监控脚本（命令行脚本，非库模块，不新增类/抽象层）：

| 入口 | 契约 |
| --- | --- |
| `python3 scripts/benchmark.py --config <path> --limit <N> --output <path>` | 输入：检测/判定/报告配置路径、批量张数、指标报告输出路径 |
| 返回值 / 退出码 | `0`：批次完整跑完（含内部错误样本被隔离记账）；非 `0`：配置非法或无法启动（如模型加载失败，统一走阶段 1 `DetectorLoadError`） |
| 输出物 | 指标报告（Markdown/JSON），含总耗时、平均/中位/最大单帧耗时、峰值内存、峰值显存、错误样本清单与计数 |

- `--limit` 默认 30；`--output` 缺省落 `reports/benchmark.md`。
- 错误计量与报告聚合口径见 §4.4 / §4.5；本脚本不复制检测逻辑，只编排既有 `Pipeline`/`ReportBuilder`。

## 7. 阶段要求与验收标准

1. 端到端 4 类输入源走全链路不崩溃。

   - 命令：`python3 -m pytest -q tests/ -k e2e`（或 `python3 scripts/benchmark.py --limit 30 --config configs/yolo_demo.yaml`）
   - 通过判据：30 张目录、单图、视频、空目录、损坏图均覆盖；除空目录（预期 `SourceOpenError`）与损坏图（预期 `InputSourceError` 或隔离记账）外，退出码 0、报告生成。

2. 空目录抛 `SourceOpenError`、不生成报告。

   - 命令：对空目录跑一次流水线并断言异常类型
   - 通过判据：`pytest.raises(SourceOpenError)`，且 `reports/` 下**不新增**报告文件。

3. 损坏图片不中断批次。

   - 命令：`python3 scripts/benchmark.py --limit 30 ...`（样本目录内混入 1 张损坏图）
   - 通过判据：脚本退出码 0，错误清单计数 = 损坏图张数（如 1），其余 29 张正常产出，报告样本数 = 29。

4. 性能达标。

   - 命令：`python3 scripts/benchmark.py --limit 30 ...`，读取输出指标
   - 通过判据：检测 FPS ≥ 20（单帧 ≤ 50 ms）；峰值内存随批次结束回落，RSS 不随张数单调累积（无泄漏）。

5. 报告聚合一致。

   - 命令：批量跑完比对 `reports/*.pdf/xlsx` 与终端日志
   - 通过判据：报告样本数 / 合格数 / 不合格数 / 明细表行数 / 概览缺陷总数与日志统计逐字段相等（口径见 §4.5）。

6. 标准样本集结果稳定可复现。

   - 命令：同一标准集连续跑 2 次，比对两次指标与判定
   - 通过判据：两次 PASS/FAIL 判定一致，检测计数一致，耗时波动在可接受区间（写入基线表）。

## 8. 风险与注意事项

- 性能与精度的权衡需明确指标优先级，避免盲目优化（如为冲 FPS 过度跳帧导致漏检）。
- 回归测试要长期维护，否则后续改算法极易悄悄退化。
- GPU 环境与 CPU 环境表现差异大，基线需标注运行环境（§4.2）。

**特殊风险（仅点名，不在此展开）**

- 【压测脚本】在「逐图异常捕获后继续处理」存在错误样本计数与实际失败数不一致、进而与报告统计口径脱节的风险。
- 【性能监控】在「psutil 峰值内存采样」存在采样间隔导致瞬态峰值被低估的风险。
- 【端到端视频源】在「断流/中途解码失败」存在 `VideoCapture` 句柄未及时释放导致资源累计的风险。
