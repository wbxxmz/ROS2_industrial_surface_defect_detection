# 阶段技术文档审查要求

> 适用对象：阶段 0～阶段 9 共 10 篇实现技术文档。
> 本文件是十阶段共用的统一审查标准；审查任一篇前先按「一」判档，再决定跑完整版还是短版。

## 一、适用范围与风险分档

### 1.1 适用范围

- 统一适用于阶段 0～阶段 9 共 10 篇实现技术文档。
- 每篇审查先完成分档，再执行对应范围的检查项。

### 1.2 分档判据（三条，命中任一条即「完整审查」）

1. 新增或变更跨阶段接口契约（`Detection` / `Detector` / `InputSource` 等）。
2. 涉及外部资源生命周期或并发（文件/视频/摄像头/模型显存/线程）。
3. 其输出被 ≥2 个下游阶段消费。

### 1.3 分档结果

- **完整审查**：命中任一判据 → 走「二」全部 5 个子项。
- **短版审查**：三条均不命中 → 只走「2.1 接口契约」「2.4 验收标准可执行性」「2.5 衔接」三个子项；「2.2」「2.3」按「不适用」标注。

### 1.4 初判映射表

| 阶段 | 文档 | 分档 | 命中依据 |
|---|---|---|---|
| 0 | 需求与总体设计 | 完整 | 规则 1（定义契约） |
| 1 | 基础框架搭建 | 完整 | 规则 1（抽象基类契约） |
| 2 | 输入源实现 | 完整 | 规则 2（摄像头/视频资源 + 并发） |
| 3 | 传统OpenCV算法 | 完整 | 规则 3（输出被阶段 5、7 消费） |
| 4 | YOLO模型集成 | 完整 | 规则 2（模型显存/释放） |
| 5 | 结果可视化与判定 | 短版 | 均不命中 |
| 6 | 创新功能扩展 | 短版 | 均不命中 |
| 7 | 质检报告生成 | 短版 | 均不命中 |
| 8 | 集成测试与优化 | 短版 | 均不命中 |
| 9 | 部署与交付 | 短版 | 均不命中 |

> 阶段 5 / 9 若引入 `VideoWriter`、实时窗口或外部部署资源，则按规则 2 自动升级为完整审查。

## 二、通用检查项

> **不适用标注规则**：某子项/某条在本阶段无对应内容时，勾选「不适用」并写明一句话理由（如「本阶段无外部资源/并发」），不得编造内容、不得留空。

### 2.1 接口契约

- ☐ 每个对外公开函数/方法均给出签名（参数名、类型、默认值），与阶段 0 契约逐参数一致，无重命名、无改参数顺序、无改默认值。
- ☐ 返回值类型明确；返回集合时声明元素类型，并说明「无结果」时返回空集合、`None` 还是抛异常。
- ☐ 声明每个接口可能抛出的异常类型（含自定义异常类名），并指明由调用方捕获还是继续上抛。
- ☐ 逐一列出允许返回 `None` 的位置及 `None` 的业务含义；同一接口的 `None` 不得同时表示「无结果」与「出错」。
- ☐ 每个字段声明类型与单位（如坐标：像素/归一化、置信度：0~1、时间：s/ms、帧序号：int），且单位与阶段 0 契约一致。

**阶段 0 自指例外**：审查阶段 0 时，2.1 改为检查「§5 接口契约」定义是否完整到可被下游逐参数核对（每个字段/方法具备名称、类型、单位、是否可 `None`、异常语义）；不要求与自身一致，缺失项直接列为补全项。补全结果见「四」的契约表要求。

### 2.2 异常与边界

- ☐ 至少覆盖空输入、空帧、尺寸为 0 图像、损坏/不存在文件、单帧视频等输入边界。
- ☐ 每个边界情形给出可判定的预期行为（返回空 / 抛指定异常 / 记指定级别日志），不含「酌情」「视情况」。
- ☐ 覆盖数值边界：阈值取 0/1、置信度越界、空列表求 max/min、除零。

### 2.3 并发与资源生命周期

- ☐ 每个资源（文件句柄、`VideoCapture`、摄像头、模型）写明 open→使用→close 的完整生命周期。
- ☐ 明确资源所有者（谁创建谁释放），不存在「释放责任不清」。
- ☐ 声明线程模型（单线程/多线程/线程安全）；多线程共享对象时写明加锁或深拷贝策略。
- ☐ 写明异常路径下资源的释放方式（`with` / `try-finally` / 上下文管理器），保证异常时也能释放。

### 2.4 验收标准可执行性

- ☐ 每条验收标准对应一条可执行命令或一个可观测结果（可运行/可看日志/可比对输出）。
- ☐ 每条验收标准给出明确的「通过 vs 不通过」判定谓词。
- ☐ 验收标准覆盖本阶段全部交付物，且不依赖未交付的后阶段功能。

### 2.5 与前后阶段衔接

- ☐ 本阶段输出的接口签名与「消费它的下游阶段」文档中的引用逐字一致（交叉核对）。
- ☐ 本阶段消费的上游接口签名与上游文档一致。
- ☐ 前置条件（依赖）完整列出，且均为已交付或本阶段同步交付的项。

## 三、每阶段「特殊风险」填写规则

- ☐ 每篇最多 1~3 条，格式固定为一句：「【模块】在【某处】存在【某风险】」。
- ☐ 只点名风险，不写解决方案、不展开。
- ☐ 不得与「二」通用检查项重复；已被通用项覆盖的一律不填。
- ☐ 只写本阶段范围内的风险，不写下游阶段或全局问题。

## 四、审查输出格式

- ☐ 交付 = **修改后文档 + 简短修改说明**，两者缺一不可。
- ☐ 修改后文档：在原文对应位置修订，各阶段原有章节标题与顺序保持不动。
- ☐ 修改说明：按「补了什么 / 为什么补」逐条列出，每条标注改动位置（如「§5 接口契约」），不附带无关建议。
- ☐ **阶段 0 追加项**：审查阶段 0 时，输出额外包含一张「补全后契约表」，逐字段/逐方法列出 `Detection`、`Detector`、`InputSource` 的名称、类型、单位、是否可 `None`、异常语义，作为下游阶段逐参数核对的基准。

## 五、明确禁止项

- ☐ 不重构章节结构：保持各阶段原有章节标题与顺序不变。
- ☐ 不引入新模块或新抽象层：不改目录结构，不新增类/函数签名或接口。
- ☐ 不添加文档未提功能：仅审查、补全文档所述内容，不新增任何阶段目标或交付物。
- ☐ 上述禁止项同样约束「修改说明」，不得在说明中越权提议。
